No coding needed: three steps to start不会编程也能用：三步开始

You don’t install anything yourself, and you don’t need a plot worked out in advance. You have an AI assistant do the setup, then tell it you want to write a novel.

你不用自己装任何东西，也不用事先想好剧情。让 AI 助手替你装好，然后告诉它你想写小说就行。

  • Step 1第一步Get an AI coding assistant, the way you’d install any app. Inside mainland China, Qoder or Trae is the easiest route; elsewhere, Claude Code or Cursor.装一个 AI 编程助手，和装普通软件一样。大陆用 Qoder 或 Trae 最省事，海外用 Claude Code 或 Cursor。
  • Step 2第二步Paste it one paragraph from the README. It downloads the tool, checks your environment and installs whatever is missing.把 README 里的那一段话整段贴给它。它会自己下载工具、检查环境、补齐缺的东西。
  • Step 3第三步Sign up with a model provider and paste back the key — on DeepSeek, ten-odd chapters cost about a dollar. Then say “I want to write a novel.”去模型平台注册、拿一个 key 贴回给它——用 DeepSeek 写十几章大约几块钱。然后说一句「我想写小说」。

It asks which genre, how much you already have (nothing is a fine answer) and which readership, then offers several openings to choose from. After that it writes on its own; every 30 chapters it drafts a few versions of the next arc for you to pick. Chapters land as plain text files you can open with a double-click.

它会问你写什么题材、手上已经有多少（什么都没有也可以）、写给哪类读者，然后给你几个开局方案挑。之后它就自己往下写，每 30 章会出几版后续大纲让你选一个。写好的章节就是普通的 txt 文件，双击就能读。

Those three steps are the short version. The rest of this post is about what happens underneath them: why writing one good chapter is easy and writing two hundred is not, and what it took to make a tool I built for myself usable by someone who isn’t me.

上面三步是简单版。下面讲的是这三步底下发生了什么：为什么写好一章容易、写好两百章难，以及要把一个自己用的工具变成别人也能用的，到底花了多少功夫。

The hard part was never writing a chapter难的从来不是写出一章

A serialized Chinese web novel runs several hundred chapters and six hundred thousand characters. No model holds that in context. So the difficulty is not producing one good chapter — a competent model does that on the first try. The difficulty is that chapter 200 has to remember a detail planted in chapter 3, and has to still believe it.

一本连载的中文网络小说动辄几百章、六十万字。没有任何模型的上下文装得下。所以难点不是写出一章好文字——这件事稍微像样的模型第一次就能做到。难点是第 200 章还要记得第 3 章埋下的那个细节，而且还得认它。

Everything else in the design follows from that one constraint. What a chapter can see is a layered memory, each layer holding a different kind of fact that decays at a different rate:

整个设计都是从这一条约束长出来的。写一章时能看到的是一套分层记忆，每一层装着一类衰减速度不同的事实：

  • hard_constraintsLines that must never move. Checked, not summarized.绝对不能动的红线。是被核对的，不是被压缩的。
  • story bible故事圣经What is permanently true — names, relations, the shape of the world.永远为真的东西——名字、关系、世界的形状。
  • foreshadowing ledger伏笔台账Debts taken on and not yet repaid. A novel’s most forgettable asset.欠下还没还的债。一本小说里最容易被忘掉的资产。
  • character.knowsWho knows what, and since when. Information boundaries are where long fiction breaks first.谁知道什么、从什么时候起知道。长篇最先垮掉的地方就是信息边界。
  • arc recaps往事提要Distant history, compressed to one paragraph per arc.久远的事，每条弧线压成一段。
  • arc plan弧线计划What this stretch of the book has promised to deliver.这一段书答应要兑现的东西。
  • last 10 summaries最近 10 章摘要Short-term continuity — and the layer with the sharpest edge.短期连贯性——也是边界最锋利的一层。
  • last 2 chapters, raw最近 2 章原文Voice. Summaries lose prose rhythm; only the text carries it.文风。摘要会丢掉语感，只有原文带得动。

Only the last ten summaries enter the context. Everything older is carried entirely by the layers above them. That single cutoff is the reason the foreshadowing ledger, the information boundaries and the arc recaps exist at all — each one is a specific kind of fact that would otherwise fall off the edge of chapter ten and never come back.

进上下文的摘要只有最近十章。更早的全部由上面那几层承载。正是这一条截断，才是伏笔台账、信息边界、往事提要存在的全部理由——每一样都是一类特定的事实，否则它们会从第十章的边缘掉下去，再也回不来。

Why it works even if you’ve never coded为什么不会编程也能用

The first version only ran on my own computer, where everything it needed was already set up. A beginner would have got stuck at four places. Here is what each one looks like for you now:

第一版只能在我自己的电脑上跑，因为它需要的东西我早就装好、配好了。换一个新手来用，会卡在四个地方。下面是现在每一处对你来说是什么样：

  • Use whichever AI assistant you have. Qoder and Trae are the easiest in mainland China; Claude Code, Cursor and several others work too. Without any assistant, you can still run it from the command line.手上有哪个 AI 助手就用哪个。大陆用 Qoder、Trae 最省事，Claude Code、Cursor 等也都能用。一个助手都没有，直接敲命令也能跑。
  • You don’t need OpenAI. It uses DeepSeek by default, which works from mainland China and is cheap: ten-odd chapters cost about a dollar.不需要 OpenAI。默认用 DeepSeek，大陆直接能连，而且便宜：写十几章大约几块钱。
  • You don’t need to know Python or what an API key is. The AI runs a built-in checkup, installs whatever is missing, and walks you through getting a key. Your only job is to sign up and paste the key back.不用懂 Python，也不用知道 API key 是什么。AI 会跑一遍自带的环境检查，缺什么装什么，再一步步带你拿到 key。你要做的只是注册账号，把 key 贴回给它。
  • You know right away whether it’s for you. The README’s first question is which kind of user you are. If you don’t code, it sends you straight to the five-minute start, with no installation notes to wade through.一眼就知道适不适合你。README 第一句就问你属于哪种用户。不会编程的话，直接跳到「零基础五分钟开始」，不用先啃一堆安装说明。

The writing engine barely changed along the way. What changed was everything you would otherwise have had to figure out before writing your first line.

这一路上，写作引擎本身几乎没动。变的是那些你本来要先自己搞懂、才能写出第一行字的东西。

How you know it’s working怎么确认它没出问题

You don’t have to check anything by hand. The tool checks itself at three points, and leaves every decision to you:

你不用自己动手检查什么。它会在三个地方自己检查，而每个决定都留给你：

  • Before you start. A built-in checkup lists anything missing from your setup. The AI fixes it, then runs the checkup again to confirm everything is ready.开始之前。自带的环境检查会列出还缺什么。AI 补齐之后再跑一遍，确认都准备好了。
  • After every chapter. It reviews what it just wrote: length, a repeated opening, stock AI phrases readers find grating, and whether the story broke any of your red lines, such as a mute hero suddenly speaking. Every problem comes with the passage that shows it.每写完一章。它会回头检查刚写的内容：字数、开头是不是和上一章雷同、有没有读者嫌弃的“AI 味”套话，以及有没有违反你定下的红线，比如设定是哑巴的主角突然开口说话。每个问题都附上原文作为证据。
  • You decide what gets fixed. It never rewrites a chapter on its own. You pick which problems to fix; the original is backed up first, so you can always go back.改不改由你定。它不会自作主张重写。你点名要改哪几条，改之前会先备份原稿，不满意随时可以退回。

One thing worth doing yourself: after the project is set up, read its list of red lines once — the facts that must never change, like who is dead or what the hero can’t do. Everything after chapter one is built on them.

有一件事值得你亲自做：项目建好后，把它列出的红线读一遍——那些永远不能变的设定，比如谁已经死了、主角做不到什么。第一章之后的所有内容都建在它们上面。

For developers. If you only want to write, you can stop here. The two sections below are about how the tool itself is tested and what I learned building it.

写给开发者。如果你只是想写小说，读到这里就够了。下面两节讲的是这个工具本身怎么测试，以及做它的过程中学到的东西。

Changing the tool without breaking it改了东西，怎么确认没改坏

This was the hardest part. Ordinary software has right answers: a calculator should say 2 + 2 = 4, so you can check it. A chapter of a novel has no “correct” version. If I change one line of the instructions the tool gives the AI, reading the next chapter won’t tell me whether something else quietly stopped working.

这是最难的部分。一般的软件有标准答案：计算器算 2 + 2 就该等于 4，一查就知道对不对。可一章小说没有“正确版本”。我改了工具给 AI 的一行指令，光读下一章，看不出别的地方是不是悄悄坏了。

So I don’t test the writing itself. I test everything around it that does have a right answer, in three ways. None of them costs anything to run:

所以我不测小说写得好不好，而是测它周围那些有标准答案的部分。一共三种办法，跑起来都不花钱：

196 automatic checks196 项自动检查

Is every file where it should be? After a chapter, is the story’s memory updated correctly? Are the genre templates complete? It takes a few seconds. Anyone who edits the tool can run it to make sure they haven’t broken anything.

文件是不是都在该在的地方？写完一章，故事记忆有没有正确更新？题材模版是不是完整？几秒钟跑完。谁改了这个工具，跑一遍就知道有没有改坏。

21 test requests, and the 10 it should ignore matter most21 条测试请求，最重要的是那 10 条“不该理”的

The tool should start when you ask for a novel and stay out of the way otherwise. So I wrote 11 requests that should start it, and 10 that shouldn’t. The 10 are the real test, because they use the same words: write me a year-end summary; analyze the genres of the top fifty on Fanqie; my novel website is showing an error, check the logs; what should I watch for in this novel’s licensing contract. Each one mentions writing or novels. If the tool is set up even a little too loosely, it passes all 11 and wrongly jumps in on these 10 — and you would never notice unless you had written them down in advance.

这个工具应该在你要写小说时启动，其他时候别插手。所以我写了 11 条应该启动它的请求，和 10 条不应该启动的。那 10 条才是真正的考题，因为它们用的是同一批词：帮我写一篇年终总结；分析番茄免费榜前五十的题材分布；我的小说网站报错了，帮我看日志；这本小说的版权合同该注意什么。每一条都提到了写作或小说。工具只要设得稍微宽一点，11 条全过，却会在这 10 条上乱插手——而如果你没有事先把它们写下来，根本发现不了。

Checking the numbers in the docs核对文档里的数字

The docs say things like “196 checks” or “37 genres”. As the project grows, those numbers go out of date, and nobody goes back to recount. So one of the automatic checks counts for real and fails if the docs say something different. It was needed: after a few dozen checks were added, two files still said 132 and a third said 104, when the real count was already 163.

文档里会写“196 项检查”“37 个题材”这样的数字。项目一长大，这些数字就过时了，而且没人会回头重数。所以有一项自动检查会去实际数一遍，和文档对不上就报错。这是被逼出来的：加了几十项检查之后，两个文件还写着 132、第三个写着 104，而实际已经有 163 项。

Automatic checks miss things too. One check in the project makes sure the numbers in the docs are right, but it only recognises a few fixed ways of writing them. One file said “97” in a different wording, and the check never noticed — until I counted by hand while writing this post. I’ve since taught it that wording, but the next new wording will slip past just the same. So automatic checks don’t replace checking by hand now and then.

自动检查也会漏。项目里有个检查专门核对文档里的数字对不对，但它只认得几种固定写法。有一个文件换了种说法写「97 项」，它就没认出来——直到我写这篇文章时手动数了一遍才发现。后来我让它也认得这种写法了，但以后换一种新说法，它照样会漏。所以自动检查不能代替偶尔手动核对。

Lessons that apply beyond novels小说之外也用得上的经验

Three things I learned building this, and none of them is specific to novels. They apply to almost any AI tool.

做这个项目学到了三条经验，没有一条是小说特有的，换到别的 AI 工具上也一样适用。

  • Test when it should do nothing. If you only test the jobs a tool is meant to do (“help me write a novel” → it starts), it will always look perfect. The real test is a set of requests that aren’t its business, like “write me a year-end summary”, to see whether it barges in anyway.先想清楚“什么时候不该做”。只测它该干的活（说“帮我写小说”时启动），它看起来永远完美。真正要测的是一批“不该它管”的请求，比如“帮我写年终总结”，看它会不会乱插手。
  • If something has no right answer, test the parts around it that do. There’s no right or wrong for whether a chapter is good. But whether the chapter file was saved, or the story’s memory was updated correctly, does have a right answer. Not being able to test the core is no reason to give up on testing altogether.没有标准答案的东西，就测它周围有标准答案的部分。一章小说写得好不好，没法判对错；但章节文件存好了没有、故事记忆更新对了没有，是能判对错的。不能因为核心没法测，就整个放弃测试。
  • Check the documentation too. Every number in it — how many checks, how many genres — is a promise to the reader. It goes out of date as soon as the project changes, and nobody goes back to recount on their own.文档也要检查。文档里写的数字（多少项检查、多少个题材）都是对读者的承诺，项目一改就过时，而且没人会主动回头去数。
