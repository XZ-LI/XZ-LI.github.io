No coding needed: three steps to start不会编程也能用：三步开始

You don’t install anything yourself, and you don’t need a plot worked out in advance. You have an AI assistant do the setup, then tell it you want to write a novel.

你不用自己装任何东西，也不用事先想好剧情。让 AI 助手替你装好，然后告诉它你想写小说就行。

  • Step 1第一步Get an AI coding assistant, the way you’d install any app. Inside mainland China, Qoder or Trae is the easiest route; elsewhere, Claude Code or Cursor.装一个 AI 编程助手，和装普通软件一样。大陆用 Qoder 或 Trae 最省事，海外用 Claude Code 或 Cursor。
  • Step 2第二步Paste it one paragraph from the README. It downloads the tool, checks your environment and installs whatever is missing.把 README 里的那一段话整段贴给它。它会自己下载工具、检查环境、补齐缺的东西。
  • Step 3第三步Sign up with a model provider and paste back the key — on DeepSeek, ten-odd chapters cost about a dollar. Then say “I want to write a novel.”去模型平台注册、拿一个 key 贴回给它——用 DeepSeek 写十几章大约几块钱。然后说一句「我想写小说」。

It asks which genre, how much you already have (nothing is a fine answer) and which readership, then offers several openings to choose from. After that it writes on its own; every 30 chapters it drafts a few versions of the next arc for you to pick. Chapters land as plain text files you can open with a double-click.

它会问你写什么题材、手上已经有多少（什么都没有也可以）、写给哪类读者，然后给你几个开局方案挑。之后它就自己往下写，每 30 章会出几版后续大纲让你选一个。写好的章节就是普通的 txt 文件，双击就能读。

Those three steps are the short version. The rest of this post is about what happens underneath them: why writing one good chapter is easy and writing two hundred is not, and what it took to make a tool I built for myself usable by someone who isn’t me.

上面三步是简单版。下面讲的是这三步底下发生了什么：为什么写好一章容易、写好两百章难，以及要把一个自己用的工具变成别人也能用的，到底花了多少功夫。

The hard part was never writing a chapter难的从来不是写出一章

A serialized Chinese web novel runs several hundred chapters and six hundred thousand characters. No model holds that in context. So the difficulty is not producing one good chapter — a competent model does that on the first try. The difficulty is that chapter 200 has to remember a detail planted in chapter 3, and has to still believe it.

一本连载的中文网络小说动辄几百章、六十万字。没有任何模型的上下文装得下。所以难点不是写出一章好文字——这件事稍微像样的模型第一次就能做到。难点是第 200 章还要记得第 3 章埋下的那个细节，而且还得认它。

Everything else in the design follows from that one constraint. What a chapter can see is a layered memory, each layer holding a different kind of fact that decays at a different rate:

整个设计都是从这一条约束长出来的。写一章时能看到的是一套分层记忆，每一层装着一类衰减速度不同的事实：

  • hard_constraintsLines that must never move. Checked, not summarized.绝对不能动的红线。是被核对的，不是被压缩的。
  • story bible故事圣经What is permanently true — names, relations, the shape of the world.永远为真的东西——名字、关系、世界的形状。
  • foreshadowing ledger伏笔台账Debts taken on and not yet repaid. A novel’s most forgettable asset.欠下还没还的债。一本小说里最容易被忘掉的资产。
  • character.knowsWho knows what, and since when. Information boundaries are where long fiction breaks first.谁知道什么、从什么时候起知道。长篇最先垮掉的地方就是信息边界。
  • arc recaps往事提要Distant history, compressed to one paragraph per arc.久远的事，每条弧线压成一段。
  • arc plan弧线计划What this stretch of the book has promised to deliver.这一段书答应要兑现的东西。
  • last 10 summaries最近 10 章摘要Short-term continuity — and the layer with the sharpest edge.短期连贯性——也是边界最锋利的一层。
  • last 2 chapters, raw最近 2 章原文Voice. Summaries lose prose rhythm; only the text carries it.文风。摘要会丢掉语感，只有原文带得动。

Only the last ten summaries enter the context. Everything older is carried entirely by the layers above them. That single cutoff is the reason the foreshadowing ledger, the information boundaries and the arc recaps exist at all — each one is a specific kind of fact that would otherwise fall off the edge of chapter ten and never come back.

进上下文的摘要只有最近十章。更早的全部由上面那几层承载。正是这一条截断，才是伏笔台账、信息边界、往事提要存在的全部理由——每一样都是一类特定的事实，否则它们会从第十章的边缘掉下去，再也回不来。

The rewrite that mattered: the user is not me真正的重写：使用者不是我

The first version worked. It worked on my machine, through my coding agent, against a model my network could reach, with keys I had already configured. Read as a list, the commits that followed are not features. They are assumptions being removed one at a time:

第一版是能跑的。在我的机器上、通过我用的编程助手、连着我的网络能连上的模型、用我早就配好的 key。后面那串提交，当成清单读的话，它们不是功能，而是一条一条被拆掉的假设：

  • Assumed one agent. Unbound from any single tool; entry files generated for several, including Qoder and Trae, the two most used in mainland China.假设了只有一个 agent。解除与单一工具的绑定；为多家生成入口文件，包括大陆最常用的 Qoder 和 Trae。
  • Assumed OpenAI was reachable. For a user writing Chinese web fiction from inside mainland China, it is not. The default moved to DeepSeek.假设 OpenAI 连得上。对一个在大陆写中文网文的人来说，连不上。默认改成了 DeepSeek。
  • Assumed Python and an API key. Added an environment doctor, a one-command key setup, and a route through for someone who has never seen either.假设用户懂 Python、有 API key。加了环境自诊、一条命令配 key，以及一条给从没见过这两样东西的人走的路。
  • Assumed one kind of reader. The README now forks by reader on line one, instead of making a novelist read installation notes to find out whether this is for them.假设读者只有一种。README 现在第一行就按读者分叉，而不是让一个写小说的人先读完安装说明，才知道这东西是不是给他的。

The capability was never the bottleneck. The preconditions were. A tool that requires its user to already be its author is not a tool yet, and the distance between those two states turned out to be most of the work.

瓶颈从来不在能力，而在前置条件。一个要求使用者先变成作者本人才能用的工具，还不算工具；而这两种状态之间的距离，才是绝大部分工作量。

How do you know you didn’t break it?怎么知道你没把它改坏？

Here is the part I expected to be hardest, and was. The output is fiction. There is no correct answer to compare against, no assertion that says a chapter is right. Change one line of a prompt and you cannot tell from reading whether anything downstream quietly stopped working.

这是我预期最难、结果也确实最难的部分。产出是小说。没有正确答案可以对照，没有任何断言能判定一章「对」。改一行提示词，你光读是读不出来下游有没有什么东西悄悄不工作了。

So I stopped trying to test the prose and tested everything around it that is deterministic. Three layers, none of which calls a paid API:

于是我不再试图测文字本身，转而去测它周围所有确定的东西。三层，没有一层会调用付费接口：

194 deterministic self-checks194 项确定性自检

Structure, file contracts, state transitions, template integrity. Runs in seconds, costs nothing, and is the thing a user runs after editing the skill to confirm they haven’t broken it.

结构、文件契约、状态流转、模版完整性。几秒跑完，不花钱，是用户改完 skill 之后用来确认没改坏的那一下。

A 21-query trigger set — and the 10 negatives are the test21 条触发测试——10 条反例才是真正的考题

A skill has to fire on the right requests and stay quiet on the wrong ones. Eleven queries should trigger it. Ten should not, and those ten are the whole point, because they share its vocabulary: write me a year-end summary; analyze the genre distribution of the top fifty on Fanqie; my novel site is returning a 500, check the logs; what should I watch for in this novel’s licensing contract. Every one of them contains a word the skill is listening for. A description written even slightly too broadly passes all eleven positives and fails these — and the failure is invisible unless you wrote the negatives down first.

一个 skill 既要在该触发时触发，也要在不该触发时闭嘴。11 条提问应该触发它。10 条不应该，而这 10 条才是全部重点，因为它们和它共用词汇：帮我写一篇年终总结；分析番茄免费榜前五十的题材分布；我的小说网站报 500，帮我看日志；这本小说的版权合同该注意什么。每一条里都有这个 skill 正在监听的词。描述只要写得稍微宽一点，11 条正例全过，这 10 条全挂——而且除非你事先把反例写下来，否则这种失败你根本看不见。

The self-check checks the documentation’s own numbers让自检去核对文档自己的数字

Documentation makes quantitative claims — how many checks, how many scripts, how many genre templates — and those claims rot silently, because nobody goes back to recount. So the suite greps its own docs for advertised figures and fails when they disagree with reality. It had to: after a few dozen checks were added, two files still advertised 132 and a third said 104, when the real count had reached 163.

文档会给出可量化的承诺——多少项检查、多少个脚本、多少个题材模版——而这类承诺会无声地烂掉，因为没有人会回头重数一遍。所以自检会去抓自己文档里的宣传数字，对不上就判失败。这条是被逼出来的：加了几十项检查之后，两个文件还写着 132、第三个写着 104，而真实数字已经到了 163。

A guard is only as wide as its pattern. That check matches several phrasings of “N checks” — and a stale 97 in a differently-worded line slipped straight past it. The lesson is not that the guard was wrong to exist. It is that a guard against drift is itself a thing that drifts, and the only reason I found this one is that I went back and ran the count by hand before quoting it here.

一道防线的宽度，不会超过它那条正则。那项检查能匹配好几种「N 项检查」的写法——而另一种措辞里一个过期的 97 就这么直接溜了过去。教训不是这道防线不该存在，而是：防漂移的机制本身也会漂移；我之所以发现它，只是因为要把这个数字写进这篇文章，所以回头手动数了一遍。

What carries over可以带走的部分

Three things, none of them specific to fiction. Write the negative cases first, because a system that only ever sees what it should match will look perfect. When there is no ground truth, test the deterministic shell around the thing you cannot score, rather than giving up on testing. And treat documentation as an artifact under test, because every number in it is a claim, and claims decay faster than code.

三件事，没有一件是小说特有的。先写反例，因为一个只见过「该匹配什么」的系统看起来永远完美。没有标准答案时，去测你没法打分的那个东西周围那层确定的壳，而不是干脆放弃测试。以及，把文档当作被测对象，因为文档里的每一个数字都是一句承诺，而承诺烂得比代码快。
